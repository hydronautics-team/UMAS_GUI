# Архитектура UMAS GUI

## Взаимодействие с ROS 2

`RosBridge` расположен в `src/integrations/ros` и работает в отдельном `QThread`. Он связывает Qt-интерфейс с узлами `stingray_core`.

Основные входящие данные:

- `/core/state/odometry` — положение, ориентация и скорость;
- `/stingray_core/battery/state` — состояние аккумуляторов.

Основные исходящие команды:

- `/control/data` (`geometry_msgs/msg/Twist`) — управляющие воздействия;
- `/control/loop_flags` (`std_msgs/msg/UInt8`) — флаги контуров управления.

## Запись rosbag

Управление локальной записью реализовано отдельным классом `RosbagRecorder` в
`src/integrations/rosbag`. Он запускает `ros2 bag record` напрямую через
`QProcess`, без shell, и не связан с потоком выполнения `RosBridge`.

Запись запускается и останавливается из меню «Запись». При штатной остановке
процесс сначала получает `SIGINT`, чтобы rosbag успел завершить файл и записать
metadata. Текущий статус отображается в status bar.

Корневой каталог задаётся переменной окружения `UMAS_ROSBAG_DIR`. Команда
`umas-gui run` устанавливает его в `/UMAS_GUI/bags` — каталог `bags` в корне
репозитория, уже подключённого к контейнеру. Поэтому записи сохраняются на хосте
после удаления контейнера. Для каждой записи создаётся отдельный каталог с датой
и временем; сам `bags` исключён из Git.

Сейчас список записываемых топиков задаётся в `setupRosbagRecording()` в
`src/app/mainwindow.cpp`. Для запуска записи среда приложения должна содержать
CLI-команду `ros2` и пакеты `ros2bag` и `rosbag2_storage_default_plugins`.

## Рабочие пространства главного окна

Верхний уровень интерфейса разделён на три независимых рабочих пространства:

- «Управление» содержит существующий операторский экран, видео, органы ручного и
  автоматизированного управления;
- «Автономная миссия» предназначена для плана, маршрута, текущего этапа,
  прогресса и журнала событий миссии;
- «Диагностика» предназначена для готовности аппарата, состояния подсистем,
  активных неисправностей и подробных результатов проверок.

Элементы новых разделов уже имеют отдельные `objectName`, но действия миссии и
кнопка запуска проверки заблокированы до подключения соответствующих ROS API.
Кнопка `diagnosticsPreflightButton` является точкой интеграции с
`stingray_core_doctor`; длительные проверки не должны выполняться в GUI-потоке.

## Структура проекта

```text
src/
├── app/                 # точка входа и главное окно
├── core/                # состояние и прикладная логика
├── integrations/        # ROS, видео и устройства ввода
├── ui/                  # приборы и панели интерфейса
└── features/            # функции, подготовленные для будущих режимов

resources/               # изображения и Qt-ресурсы
docker/                  # Dockerfile контейнера
docs/                    # документация
archive/                 # отключённые модули для дальнейшей адаптации
```

`src/features/automatic/algorithm_cpp` подключён как внешний submodule и сохраняет
собственную структуру. Обёртка для будущего автоматического режима находится рядом.

Старые модули карты, автоматического режима и служебных панелей сохранены в
`archive/legacy-ui`. Они намеренно не подключены к CMake и текущему приложению.
